# AI 教学问答实现文档

## 1. 功能入口

### 全局问答

适合询问算法概念、学习方法、训练计划解释和内部资料。没有具体题目上下文时，AI 不应假装知道用户正在做哪道题。

### 题目助教

题目页面传递 `problemId`、`trainingId`、`contestId` 和当前用户状态。后端重新查询题目和权限，不能相信前端传来的题目文本。

### 提交分析

用户主动选择某次提交后，后端获取用户有权限查看的代码、编译信息和评测结果，再发送给模型。分析结果应重点解释错误类型、复杂度和边界，不直接替用户提交修改后的代码。

## 2. 分层教学模式

建议提供明确的教学级别：

1. **只问问题**：AI 通过反问帮助学生定位思路。
2. **轻提示**：只指出知识点和观察方向。
3. **思路提示**：给出算法方向和关键不变量，不给完整实现。
4. **实现检查**：学生提交自己的思路或代码，AI 检查问题。
5. **完整讲解**：仅在非比赛、允许的普通题目场景开放。

默认级别为 2。用户每次主动点击“继续提示”才升级，避免一次性泄露答案。

## 3. 推荐的回答结构

```text
理解确认
 → 本题考察的知识点
 → 一个小问题，引导学生思考
 → 当前层级的提示
 → 下一步建议
 → 相关内部资料/相似题目
```

回答末尾可以询问：

- “你现在想到的状态定义是什么？”
- “你希望继续获得提示，还是先自己尝试？”
- “要不要把你的代码或思路发给我检查？”

## 4. 请求上下文

上下文应分为四层，避免把所有数据都塞给模型：

- 系统规则：教学风格、比赛禁用、隐私规则；
- 页面上下文：题目、训练、语言、提交状态；
- RAG 上下文：检索到的内部片段；
- 对话历史：最近若干轮，过长时摘要。

代码分析时要限制代码长度，必要时只发送相关函数和错误信息。模型输出不能直接执行，不能把模型生成的代码自动提交或部署。

## 5. 会话数据

至少保存：

- 会话所属用户和入口类型；
- 题目/训练/提交关联；
- 用户消息和 AI 消息；
- 使用的模型和供应商；
- 引用来源；
- Token、耗时、错误信息；
- 用户点赞、点踩和反馈原因。

代码内容属于敏感数据，日志中只能保存摘要或脱敏信息，不应保存完整代码到普通应用日志。

## 6. 流式接口

推荐使用 SSE：

```text
POST /api/ai/chat
  → event:start
  → event:delta（多次）
  → event:source
  → event:done
```

前端断开连接时，后端要取消或标记模型请求，避免用户已经离开页面但 Token 仍持续消耗。

## 7. AI 不应做的事情

- 在比赛期间回答当前比赛题目；
- 直接读取并泄露其他用户代码；
- 把未经审核的讨论当成官方题解；
- 伪造评测结果；
- 自动替用户修改并提交代码；
- 代替后端计算用户排名、通过率和能力分数。
