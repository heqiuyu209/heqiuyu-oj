# 总体架构与职责边界

## 1. 设计原则

### HOJ 后端掌握业务事实

HOJ 后端负责用户、权限、题目、提交、训练、比赛、学习行为和 AI 会话。RAG 服务不直接决定用户是否有权限查看内容，也不直接访问浏览器。

### RAG 服务掌握检索流程

RAG 服务负责文档解析、清洗、切片、向量化、检索、重排和上下文组装。它接收 HOJ 传来的用户身份和过滤条件，只返回允许使用的片段。

### LLM 负责生成，不负责统计

模型可以解释题目、分析代码、总结计划，但“通过率”“薄弱点”“推荐分数”等关键结论应该由后端规则和数据计算得到，再让 AI 做自然语言解释。

## 2. 三条核心链路

### 问答链路

```text
用户问题
 → HOJ 鉴权与比赛状态检查
 → 生成检索范围和题目上下文
 → RAG 检索内部知识
 → 敏感信息过滤与上下文压缩
 → 选择模型供应商
 → 流式返回教学回答
 → 保存消息、引用、耗时和 Token
```

### 文档入库链路

```text
上传/同步文档
 → 文件安全检查
 → 解析为统一文本
 → 清洗并保留结构
 → 分块并生成元数据
 → Embedding
 → 写入向量库
 → 更新文档版本和任务状态
```

### 学习工作台链路

```text
提交/通过/训练/阅读/反馈
 → 学习事件
 → 后端统计知识点与能力变化
 → 生成计划和推荐候选
 → 规则排序与去重
 → AI 解释推荐原因和生成复习内容
```

## 3. 服务建议

第一版可以使用三个逻辑模块，部署时可先放在两个进程中：

- `hoj-backend`：现有 Spring Boot 后端，增加 AI、学习工作台和远程提交模块。
- `learning-os-rag`：Python RAG 服务，复用现有 `D:/learning-OS-RAG` 原型。
- `qdrant`：向量数据库；生产环境独立部署。

学习工作台不建议直接放入 RAG 服务，因为它需要查询 HOJ 的提交、训练和用户数据。RAG 只提供“相关资料”和“相关题目”的检索能力。

## 4. 比赛模式

比赛模式必须由 HOJ 后端判断，不能只依赖前端隐藏按钮：

```text
请求 AI
 → 根据 contestId 查询比赛状态
 → 比赛未开始/已结束：按规则允许
 → 比赛进行中：返回 AI_DISABLED_IN_CONTEST
```

还应在 RAG 服务和内部接口层做第二道校验。即使用户手工调用 API，也不能获取 AI 回答。

## 5. 当前需要尽早确认的工程事实

当前工作区可直接看到 HOJ 前端、API 实体模块、JudgeServer 和 DataBackup，但没有明显的业务后端源码目录。开始写 Java 代码前必须先确认业务后端的真实来源，否则无法安全地添加 Controller、Service、Mapper 和配置。
