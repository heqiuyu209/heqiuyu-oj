# 总体架构与职责边界

## 1. 设计原则

### HOJ 后端掌握业务事实

HOJ 后端负责用户、权限、题目、提交、训练、比赛、学习行为和 AI 会话。RAG 服务不直接决定用户是否有权限查看内容，也不直接访问浏览器。

### RAG 服务掌握检索流程

RAG 服务负责文档解析、清洗、切片、向量化、检索、重排和上下文组装。它接收 HOJ 传来的用户身份和过滤条件，只返回允许使用的片段。

### LLM 负责生成，不负责统计

模型可以解释题目、分析代码、总结计划，但“通过率”“薄弱点”“推荐分数”等关键结论应该由后端规则和数据计算得到，再让 AI 做自然语言解释。

## 2. 三条核心链路

### 问答链路

```text
用户问题
 → HOJ 鉴权与比赛状态检查
 → 生成检索范围和题目上下文
 → RAG 检索内部知识
 → 敏感信息过滤与上下文压缩
 → 选择模型供应商
 → 流式返回教学回答
 → 保存消息、引用、耗时和 Token
```

### 文档入库链路

```text
上传/同步文档
 → 文件安全检查
 → 解析为统一文本
 → 清洗并保留结构
 → 分块并生成元数据
 → Embedding
 → 写入向量库
 → 更新文档版本和任务状态
```

### 学习工作台链路

```text
提交/通过/训练/阅读/反馈
 → 学习事件
 → 后端统计知识点与能力变化
 → 生成计划和推荐候选
 → 规则排序与去重
 → AI 解释推荐原因和生成复习内容
```

## 3. 服务建议

沿用现有 Java 8 / Spring Boot 工程，新增业务优先按模块组织；下面是目标职责，新增服务是否可部署仍需验证：

- `hoj-backend`：现有 Spring Boot 后端，增加 AI、学习工作台和远程提交模块。
- `learning-os-rag`：Python RAG 服务，复用现有 `D:/learning-OS-RAG` 原型。
- `qdrant`：向量数据库；生产环境独立部署。

Java 业务沿用 Controller → Service → Manager → DAO/Mapper。供应商协议适配由内部 AI 服务统一实现，HOJ 负责业务用途、用户权限与配额，避免 Java/Python 重复建设适配器。原型复用程度另行核验。

客观题使用独立数据与判分模块，复用 HOJ 登录及管理权限，不经过 JudgeServer，也不改变 `Problem.type` 的 ACM/OI 含义。前端题库、作答、后台录题与错题记录需要一并接通。

学习工作台不建议直接放入 RAG 服务，因为它需要查询 HOJ 的提交、训练和用户数据。RAG 只提供“相关资料”和“相关题目”的检索能力。

## 4. 比赛模式

比赛模式必须由 HOJ 后端判断，不能只依赖前端隐藏按钮：

```text
请求 AI
 → 从登录态取得用户，服务端查比赛、时间、参赛关系及资源权限
 → 按统一策略检查所有 AI 入口、检索和工具调用
 → 受限时返回 AI_DISABLED_IN_CONTEST
```

还应在 RAG 服务和内部接口层做第二道校验。即使用户手工调用 API，也不能获取 AI 回答。

前端 contestId 只是定位提示，不能决定是否禁用；身份也不能由前端 UID 决定。流式请求跨越比赛开始时需要重新检查并终止受限输出。禁用针对参赛用户还是全站、虚拟赛及教练权限仍待确认，确认前不得自行放宽。
